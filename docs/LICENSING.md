# Licensing, for engineers

This is the internal explanation of how prism is licensed, why PRISM Hub can be
proprietary while prism is AGPL, and which specific code changes would break that. Read
it before you add a dependency, move a file between repositories, or build a distribution
artifact that contains both.

Buyer-facing version: [`../COMMERCIAL.md`](../COMMERCIAL.md).
Terms themselves (draft): [`../LICENSE-COMMERCIAL.md`](../LICENSE-COMMERCIAL.md).
Contributor rules: [`../CONTRIBUTING-CLA.md`](../CONTRIBUTING-CLA.md).

## 1. What carries which licence

| Component | Where | Licence | Notes |
|---|---|---|---|
| prism binary (`src/main.rs`, 20 subcommands) | this repo | `AGPL-3.0-only` | `Cargo.toml:7` |
| prism library (`[lib] name = "prism"`, `src/lib.rs`) | this repo | `AGPL-3.0-only` | `Cargo.toml:14-16`. The library target is the copyleft-sensitive surface — see §3. |
| ~110 `cmd` filters, PATH shims | `src/filter/`, `src/shim.rs` | `AGPL-3.0-only` | |
| Proxy, MCP server, reader, memory, graph, cache | `src/` | `AGPL-3.0-only` | |
| Test fixtures, benches, examples | `tests/`, `bench/`, `examples/` | `AGPL-3.0-only` | |
| Install / enable / disable scripts | `scripts/` | `AGPL-3.0-only` | |
| VS Code extension | `extensions/vscode/` | `AGPL-3.0-only` **by repository default** | `package.json` declares **no `license` field** — see §6.3 |
| Graph artifacts | `graphify-out/` | build output, not source | Generated; not licensed material |
| **PRISM Hub** backend + frontend | **separate repository** | **proprietary / UNLICENSED** | Not a derivative work of prism — §2 |
| Third-party crates | `Cargo.lock` | their own terms | §5 |
| The commercial licence texts | `LICENSE-COMMERCIAL.md`, `COMMERCIAL.md` | drafts, not legally reviewed | Do not treat as vetted |

The `AGPL-3.0-only` identifier is deliberate. It is not `AGPL-3.0-or-later`: recipients
get exactly AGPLv3 and not a future FSF version, which keeps the commercial position
predictable. Do not "fix" this to `-or-later`.

## 2. Why PRISM Hub is not a derivative work of prism

AGPL-3.0's copyleft attaches to a work "based on" the Program (AGPL §0), and its §13 adds
the network-source-offer obligation for a *modified* Program that users interact with
remotely. Neither reaches PRISM Hub, because every channel between the two is an
arms-length boundary between separate programs in separate address spaces, exchanging
data in a documented format.

There are exactly three channels. All three are agent-initiated; the hub never loads prism
code.

**2.1 Telemetry — HTTP.** The agent batches typed events and POSTs them to
`{hub}/api/ingest/events` (`src/hub.rs:359`, base resolved by `api_base`,
`src/hub.rs:273-281`). The payload is `camelCase` JSON, and the contract is pinned by
`tests/fixtures/hub-events.json` (regenerated by `cargo test hub::contract`) precisely so
either side can be reimplemented against the fixture rather than against the other's
source. `spool_event` is a synchronous append to a local spool file and makes no network
call at all, so the `cmd` hot path never touches the hub.

**2.2 Policy — HTTP.** `POST {hub}/api/agents/enroll` (`src/hub.rs:489`) and
`GET {hub}/api/agents/:id/config` (`src/hub.rs:548`). The hub returns configuration data —
config, filter limits, rules, a revision number. Data, not code: prism parses it into its
own types and merges it through `config.rs`'s existing precedence chain. A rules payload is
declarative filter configuration read by `src/filter/rules.rs`, not executable logic
supplied by the hub.

**2.3 MCP — stdio or Streamable HTTP.** `prism mcp --stdio` runs prism as a **separate
process** speaking JSON-RPC 2.0 over pipes (`src/mcp.rs:772-774`). `prism mcp --port <p>`
serves the same 17 tools over Streamable HTTP for a remote MCP client, including the hub's
(`src/mcp.rs:733`, `src/mcp.rs:7`). Protocol version 2026-07-28 via `rmcp` 3.2.0
(`src/mcp.rs:1-2`, `src/mcp.rs:676`) — a published third-party protocol, which is the
point: the hub is an MCP *client*, and an MCP client is not a derivative of every server it
can speak to.

**Why that matters.** Process separation plus data-only interchange over a documented
protocol is the standard basis for treating two programs as separate works — the same
reasoning that lets a proprietary program invoke a GPL command-line tool or talk to a GPL
database over a socket. The FSF's own guidance treats pipes, sockets and command-line
arguments as arms-length communication; the boundary that creates one combined work is
sharing an address space and complex internal data structures.

**Caveats worth stating out loud:**

- This is the conventional analysis, not settled law. AGPL §13's exact scope has never
  been litigated. It is the position this project operates on and it is a mainstream one,
  but it is a position, not a court ruling.
- It depends on the boundaries staying as described. §3 is the list of changes that would
  break it.
- It says nothing about *distribution* obligations for prism itself — see §4, which is the
  trap people actually fall into.

## 3. What would change the analysis

Any one of these turns prism and the other program into a single work and pulls AGPL over
that program's code. Do not do these in the hub, or in anything else proprietary.

| Change | Why it breaks |
|---|---|
| Adding `prism = { path = ... }` or a published `prism` crate dependency to another Rust program | Same address space, linked at build time — one work. |
| Wrapping `src/lib.rs` in a **napi-rs / N-API native addon** and `require()`-ing it from the hub's Node backend | The addon and the Node process share an address space. This is the specific trap for a Node-based hub, and it is tempting because it is the fastest way to call prism from TypeScript. Use HTTP or MCP instead. |
| Any FFI / `#[no_mangle]` C-ABI surface consumed in-process | Same reason. |
| Compiling prism to WebAssembly and bundling it into a proprietary frontend or worker | Same reason. Shipping the `.wasm` is also a conveyance (§4). |
| Vendoring, copying or pasting prism source into another repository | Straightforward derivation, and it also means the AGPL source must be offered for that repo's build. |
| Making prism depend on hub-proprietary code | The reverse failure: prism cannot ship as AGPL if part of it is not. |
| Re-implementing hub logic inside prism such that prism is no longer independently useful | Erodes the "separate works" story even without a code-level link. |

**The safe pattern, stated positively:** the hub talks to prism only over HTTP or MCP, or
by executing the `prism` binary as a subprocess and reading its stdout. Subprocess
execution is fine, including in a proprietary program — that is exactly what
`extensions/vscode` does.

## 4. Distribution is a separate question from derivation

This is the mistake that is easiest to make. Even where two programs are separate works
("mere aggregation", AGPL §5), putting prism's binary *inside* an artifact you distribute
is still **conveying** prism, and AGPL §6 obligations attach to that copy:

- **A Docker image containing both the hub and the `prism` binary is a conveyance of
  prism.** The hub stays proprietary — aggregation does not infect it — but whoever
  receives that image must get the AGPL text, the corresponding source for the prism
  version included (or a valid written offer for it), and no further restrictions on their
  AGPL rights.
- The same applies to any installer, appliance image, tarball, Helm chart with a baked-in
  binary, or CI artifact that a third party receives.
- Practical consequence: either do not bake prism into distributed hub images (have the
  customer install prism themselves — which is also what the agent model implies), or
  attach the notices and source offer. Decide this before the first customer-delivered
  image is built.
- Internal images that never leave your own infrastructure are not conveyances.

## 5. Inbound dependency licences

prism can only be sold commercially to the extent Licensor can license what it ships.
Third-party crates are not Licensor's to relicense.

As of `Cargo.lock` at 374 packages, a scan of the resolved tree found:

- **No GPL-, AGPL-, or LGPL-only package.** Nothing in the tree blocks a commercial
  licence. This is the single most important inbound fact and it should be re-verified
  automatically.
- Overwhelmingly `MIT`, `Apache-2.0`, `MIT OR Apache-2.0`, plus `Unicode-3.0`, `ISC`,
  `BSD-2/3-Clause`, `Zlib`, `0BSD`, `CDLA-Permissive-2.0` — all permissive.
- **`MPL-2.0`** on at least `colored` (a *direct* dependency, `Cargo.toml`) and
  `option-ext` (transitive, via `dirs-sys`), with `webpki-root-certs` to be confirmed.
  MPL-2.0 is **file-level** copyleft: MPL files may be combined with proprietary code and
  the larger work distributed under other terms (MPL §3.3), but those files stay MPL and
  their source must be available to recipients. This is compatible with selling a
  commercial licence; it is not compatible with claiming to relicense them, which
  `LICENSE-COMMERCIAL.md` §8 is careful not to do.
- `r-efi` is tri-licensed `MIT OR Apache-2.0 OR LGPL-2.1-or-later`; take MIT. It is a UEFI
  target crate and is unlikely to be built at all on the supported platforms.
- 12 of 374 packages could not be resolved from the local registry cache and were not
  classified.

**Action:** add a licence gate to CI rather than repeating this by hand.
`.github/workflows/ci.yml` already exists; `cargo deny check licenses` with an allowlist
(and an explicit exception list for the MPL-2.0 crates) is the standard way, and it fails
the build the day a copyleft transitive dependency arrives. Until that job exists, this
section is a snapshot with a shelf life.

## 6. Housekeeping the dual-licensing position depends on

**6.1 SPDX headers.** There are none today (`grep -rn SPDX src/` returns nothing across 40
`.rs` files). Per-file identifiers matter more for a dual-licensed project than for a
single-licensed one: they are the per-file evidence of what was licensed under what, they
survive file moves and code copying, and they make it visible when a file arrives from
elsewhere under different terms. Use [`../scripts/add-spdx-headers.sh`](../scripts/add-spdx-headers.sh):

```bash
scripts/add-spdx-headers.sh --dry-run      # show what would change
scripts/add-spdx-headers.sh                # apply
scripts/add-spdx-headers.sh --check        # CI gate: fail if any file lacks a header
```

The header goes on line 1, followed by a blank line, above any `//!` module doc. That
placement is safe: a plain `//` comment is whitespace to the parser and rustdoc still
picks up the `//!` block below it (verified with a standalone `rustdoc` run). Do **not**
insert the header in the middle of a `//!` block.

**6.2 The copyright holder is not yet a legal person.** `Cargo.toml:8` says
`authors = ["PRISM Team"]` and `README.md:430` asserts "Copyright (c) 2026 PRISM Team".
Neither is evidence of ownership and "PRISM Team" cannot sign a contract. See
[`../CONTRIBUTING-CLA.md`](../CONTRIBUTING-CLA.md) §1–2 — this blocks the first sale, not
the code.

**6.3 The VS Code extension declares no licence.** `extensions/vscode/package.json` has no
`license` (and no `repository`) field. Inside this repository it inherits AGPL-3.0-only by
default, but a marketplace-published extension with no declared licence is an ambiguity a
buyer's counsel will find. Add `"license": "AGPL-3.0-only"` — or make a deliberate
decision that the thin extension shell is permissively licensed while the binary it
invokes stays AGPL, which is a legitimate and quite common split for an editor plugin that
only shells out.

**6.4 `LICENSE` is verbatim AGPLv3** with the FSF's own header (`LICENSE:1-6`) and no
filled-in "how to apply" appendix. Filling in the appendix (program name, copyright line)
is conventional and helps provenance; it needs §6.2 resolved first.

## 7. What contributors are agreeing to

Short version: a contribution licensed to the project under AGPL-3.0 **alone** cannot be
included in a commercial licence, so the project cannot accept one.

- Every contribution must come with a grant that lets the maintainer license the
  contributed code under **both** AGPL-3.0-only and proprietary commercial terms.
- A DCO sign-off (`git commit -s`) is **not sufficient** on its own for this: it certifies
  provenance and the right to submit under the project's existing licence. It does not
  grant relicensing rights.
- The mechanism, the reasoning, and the draft agreement are in
  [`../CONTRIBUTING-CLA.md`](../CONTRIBUTING-CLA.md).
- If you are reviewing a pull request: do not merge until the CLA check passes. A merged
  contribution without a grant is expensive to unwind — it means either rewriting the code
  or chasing the contributor for a retroactive signature, and until then every commercial
  licence sold arguably covers code the seller cannot license.

## 8. Quick reference

| Question | Answer |
|---|---|
| Can I run prism in CI at work? | Yes, no licence needed. |
| Can I patch prism for internal use and not publish? | Yes. AGPL does not restrict private modification. |
| Can I put prism in our product's installer? | Not under AGPL unless the product is AGPL. Commercial licence (OEM). |
| Can our Node service call prism? | Over HTTP/MCP/subprocess: yes, AGPL is fine. Via a native addon in-process: no — that is one work. |
| Can I ship a Docker image with the hub and prism in it? | The hub stays proprietary, but you are conveying prism: AGPL notices + source offer required. |
| Can I offer prism-as-a-service? | Unmodified: yes, point users at the public source. Modified: publish the modifications, or buy a commercial licence. |
| Can I use the PRISM name for my product? | No. See `LICENSE-COMMERCIAL.md` §9. |
| Do I need a licence key to run prism? | No. prism performs no licence check and contacts no licence server. |
